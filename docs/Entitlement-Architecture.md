# P0-WORKER — decided 2026-07-23: **the engine verifies Google's signature**

Neither option the spec offered. Recorded here because P4 builds against it and because it
turns on an invariant, not a preference.

| | A: Entitlement Worker (spec's pick) | B: Phone-only | **C: Engine verifies Google's signature** |
| --- | --- | --- | --- |
| Anti-piracy | Strong | **Trivially bypassed** — a rooted phone patches the app to always assert Pro | Strong — Google's signature is unforgeable |
| New server | **Yes, and it is not blind** | None | **None** |
| New secrets to manage | GCP service account + Ed25519 voucher key | None | None (a *public* key is embedded) |
| Who is trusted | Our Worker | **The attacker's own device** | Google |
| Availability coupling | Pro breaks if the Worker is down (needs a grace window) | None | None — verification is offline |

## Why C, and why A was actually disqualified

`CLAUDE.md` states: *"The only planned server component is a future blind,
end-to-end-encrypted relay for an Android dashboard — **nothing else**."*

An entitlement Worker is a **second** server component, and it is **not blind** — it sees
Play purchase tokens paired with pairing ids. Choosing A therefore does not merely add ops
burden; it requires amending a stated invariant, which is a product-scope decision rather
than an implementation detail. C reaches comparable anti-piracy strength while leaving the
invariant untouched, so the invariant decides it.

B was never really viable: the phone is the attacker's device, so a phone-attested
entitlement is an honour system.

## How C works

Play Billing returns, alongside each purchase, a payload Google itself signed:

- `Purchase.getOriginalJson()` — the purchase record (`orderId`, `packageName`,
  `productId`, `purchaseTime`, `purchaseToken`, `purchaseState`, `acknowledged`).
- `Purchase.getSignature()` — RSASSA-PKCS1-v1_5 over that exact JSON, made with the app's
  RSA key pair generated by Play. The **public** half is in Play Console under *"Your
  License Key for This Application"*, base64 X.509 `SubjectPublicKeyInfo`.

Flow:

1. Phone reads its purchases via `queryPurchasesAsync` and forwards `{original_json,
   signature}` inside an `entitlement` envelope — **through the existing E2EE channel**, so
   the relay sees only ciphertext, as with everything else.
2. Engine verifies the RSA signature against the embedded Play public key
   (`RSA.VerifyData(..., HashAlgorithmName.SHA1, RSASignaturePadding.Pkcs1)` — native .NET,
   no dependency), then checks `packageName`, `productId ∈ {pro_unlock}`, and
   `purchaseState == PURCHASED`.
3. On success the engine enables the Pro panels and appends an audit event recording the
   entitlement and the device key fingerprint that delivered it.
4. The phone re-forwards on each launch. Refunds and revocations propagate because Play
   stops returning the purchase as owned, so the engine stops being told it is entitled —
   after a grace window rather than instantly (see below).

The phone is **not** trusted in this design. It is a courier for a Google-signed
assertion, and the engine is the verifier.

## The two honest weaknesses

**1. Google's IAB signature is `SHA1withRSA`.** SHA-1 is collision-broken, and given the
program's [post-quantum posture](Post-Quantum-Posture.md) that deserves stating plainly
rather than burying.

Assessment: not practically exploitable *here*. Forging would need a chosen-prefix
collision against a specific RSA key, which requires attacker control over the signed
bytes — and every field in the purchase JSON is Google-generated (`developerPayload`, the
one historically attacker-influenceable field, is gone). The payload also arrives inside
the E2EE channel from an already-paired device, so an attacker who could inject it has
already compromised the pairing and has better options.

This is nonetheless the strongest argument for keeping A available: the Play Developer API
returns entitlement data over TLS with no SHA-1 anywhere. **If Pro revenue ever justifies
the ops burden, revisit** — the `EntitlementService` abstraction below makes that a
configuration change rather than a rewrite.

**2. Revocation is not instant.** Verification is offline, so a refund is noticed when the
phone next reports (launch, or the sync cadence). The spec already anticipated a 30-day
desktop grace window for offline use; C makes that window the revocation latency too.
Acceptable for a $2.99 one-time unlock. It would **not** be acceptable for a subscription,
which matters when Cloud arrives — Cloud should not reuse this path.

## What P4 builds

`EntitlementService` keeps the spec's §6.3 abstraction — one interface, product ids in
configuration — so the verification *strategy* is swappable:

- `GoogleSignedPayloadVerifier` (C) — ships in P4.
- `DeveloperApiVerifier` (A) — not built; the seam exists so it can be added without
  touching feature flags or the envelope format.

Product id: **`pro_unlock`, INAPP, $2.99** ([P-MONEY](Monetization-Decision.md)). Cloud, as
a subscription, gets its own product and its own verification path — explicitly not this
one, per weakness 2.

Restore-purchases is first-class: reinstall or new phone re-runs `queryPurchasesAsync` and
re-forwards. Nothing about entitlement is stored only on the phone.

## Protocol impact

Payload kind `entitlement` already exists in `Sync-Protocol.md` §4.3 with body `{voucher}`.
That field name assumed option A's signed voucher. **Amend to
`{original_json, signature}`** in the same commit that implements P4, per the drift-trap
rule — and add entitlement vectors (valid signature, tampered JSON, wrong productId, wrong
packageName, non-PURCHASED state) so both implementations agree on rejection reasons.
